  • GraphQL VS REST API


  • GitHub/Front GitHub/Back


  • Fullstack projekt: I detta projekt jämfördes GraphQL och REST API:er ur ett frontendperspektiv, med fokus på datasäkerhet, autentisering och hantering av känslig information. För att möjliggöra jämförelsen byggdes en enkel bokhanteringsapplikation där båda API:erna implementerades på backend, men frontend utvecklades endast för GraphQL-versionen. Skillnader i datainhämtning, åtkomstkontroll med JWT och RBAC, cache och felhantering analyserades. Resultatet visade att GraphQL erbjuder hög flexibilitet men ökad komplexitet kring säkerhet och cache, medan REST har en tydligare struktur som förenklar säkerhetsarbetet. Slutsatsen var att frontendutvecklare, särskilt vid användning av GraphQL, behöver förstå backendarkitektur och säkerhetsprinciper. Det yttersta ansvaret för säkerheten ligger dock alltid på serversidan, vilket gör nära samarbete mellan frontend och backend avgörande.

    Säkerhetsfunktioner: JWT-token (JSON Web Token), Saltade lösenod, RBAC

    (JavaScript,HTML,CSS,React.js,Node.js,MongoDB Atlas,GraphQL API[Apollo Server], REST API[Express.js])

  • RPG Console App (Java, OOP)


  • GitHub


  • Java projekt: En enkel RPG-applikation utvecklad i Java. Projektet fokuserar på objektorienterad design med abstrakta klasser, arv och enhetstester.

    Viktiga punkter (Objektorientering i praktiken)
    • Abstraktion & arv:
    • Abstrakta klasser (Hero, Item) samlar gemensam funktionalitet, medan subklasser implementerar specifika beteenden.
    • Inkapsling:
    • Hjältars attribut och utrustning hanteras via publika metoder som Equip, LevelUp och Display.
    • Polymorfism:
    • Beräkning av skada och attribut sker olika beroende på Hero-klass (t.ex. Mage, Rogue), men anropas via den abstrakta metoden getDamagingAttribute() i den abstrakta Hero-klassen. På så sätt kan samma metodanrop, damage(), ge olika resultat beroende på Hero-klass.
    • Undantagshantering:
    • Anpassade undantag (InvalidWeaponException, InvalidArmorException) säkerställer att ogiltig utrustning inte kan användas.
    • Modularitet & testbarhet:
    • Alla publika metoder verifieras med JUnit-enhetstester.
    Beräkningslogik:
    • ●Totala attribut = grundvärden från nivå (beroende på hjälteklass) + bonus från rustning (Armor)
    • ●Skada = vapenskada × (1 + huvudattribut/100), där huvudattribut bestäms av hjälteklass (Strength, Dexterity, eller Intelligence)

    (Java, Maven)


  • Analys för hälsoundersökningar


  • GitHub/Back


  • Fullstack projekt: Jag utvecklade både front-end och back-end. Systemet gör det möjligt för analytiker att analysera olika typer av hälsoundersökningsdata och har en funktion för kors-tabellering av frågevariabler. I denna applikation användes PivotTable.js för att kunna sammanställa och visualisera undersökningsdata dynamiskt. Därför strukturerades API-svaret i ett JSON-format med en array av objekt, på samma sätt som i PivotTable.js-exemplet (t.ex. mps.json). På backend-sidan använde jag PostgreSQL och Java (Spring Boot), med fokus på strukturerad SQL-kod och effektiv databehandlingsdesign. Specifikt definierades en subfråga för varje fråge-ID (question_id), och dessa slogs samman med hjälp av patient-ID (patient_id). På så sätt skapades en intermediär tabell i SQL, där varje rad motsvarar en patient och varje kolumn representerar svaret på en specifik fråga. Denna tabell formaterades sedan till JSON-format (t.ex. samma struktur som mps.json) som det slutliga resultatet. Detta gör det möjligt att returnera data från API:t i ett format som direkt kan användas av analysverktyg som PivotTable.js, vilket eliminerar behovet av komplex datakonvertering på front-end-sidan.

    (Java, Spring Boot,JPA/Hibernate,PostgreSQL,React.js,PivotTable.js)
